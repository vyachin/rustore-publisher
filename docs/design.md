# Контракт и устройство rustore-publisher 0.0.1

Этот документ — единственный источник подробных проектных решений. Реализация
идёт: пять команд, архивы выпуска и GitHub Actions готовы; остались проверка
на живом аккаунте и тег `v0.0.1`. Непроверенные на живом аккаунте свойства API
отмечены явно. План и состояние работ
находятся в [TODO.md](../TODO.md), правила — в [AGENTS.md](../AGENTS.md).

Команды: `doctor`, `status`, `version`, `completion`, `publish`. Режим по умолчанию —
MANUAL; ручной выпуск выполняется в консоли. --draft, досылка и удаление существующих
черновиков через CLI не входят в 0.0.1. Отложенная публикация (`delayed`,
`--publish-at`) перенесена в 0.0.2 и в 0.0.1 отклоняется как ошибка ввода.
CLI не собирает и не подписывает AAB.
Документация, help и собственные сообщения для пользователя — на русском.

## Проверенные ограничения платформы

Это результаты изучения документации; они ещё не проверены на реальном аккаунте.

| Область | Вывод и следствие для реализации |
| --- | --- |
| Предварительные условия | Нужна активная версия приложения. Подпись AAB должна быть заранее настроена в консоли. |
| Авторизация | Подписать `keyId + timestamp` алгоритмом RSA PKCS#1 v1.5 / SHA-512, закодировать подпись в Base64 и вызвать `POST /public/auth/`. Базовый адрес API — `https://public-api-m.rustore.ru`. Передавать полученный JWE в `Public-Token`. Использовать `ttl` (в документации — 900 секунд); обновлять токен до истечения срока. Расхождение времени не должно превышать 60 секунд. |
| Загрузка | Поле multipart — `file`, один AAB до 5 ГБ, код версии выше активной. API позволяет обновлять AAB той же версии. Возможны один AAB и до 8 APK либо до 10 APK без AAB; CLI 0.0.1 загружает только один AAB. Возобновление передачи с прерванного байта не документировано. |
| Публикация | Создать черновик, загрузить файл, отправить на модерацию. `publishType` и `publishDateTime` относятся к телу создания черновика; в 0.0.1 CLI передаёт только `manual` или `instantly` без даты. У commit — query-параметр `priorityUpdate`, передаём 0. Успешная отправка не означает доступность пользователям; режим по умолчанию CLI — MANUAL, API — INSTANTLY. |
| Ручной выпуск | Метод публикации требует одобрения модерации и ручного режима публикации. |
| Черновики | Документация создания одновременно описывает ограничение одним черновиком и удаление предыдущего при создании нового. Считать создание потенциально разрушительной операцией; не повторять запрос вслепую. |
| Редактирование | В обзоре сказано, что черновики нельзя редактировать, но отдельный метод PATCH v2 описывает редактирование до отправки. Проверить этот метод на тестовом приложении, прежде чем использовать его для восстановления. |
| Разрешения | Новые чувствительные разрешения могут потребовать деклараций в консоли; запрещённые разрешения требуют исправления сборки. Возвращать понятную ошибку с дальнейшими действиями вместо повторных попыток. |
| Поэтапная публикация | Только 5/10/25/50/75/100 процентов, только увеличение. Режим или дату публикации нельзя менять одним запросом настроек вместе с процентом. Это за пределами версии 0.0.1. |
| Тестовые каналы | Методы статусов и подробностей упоминают alpha и типы тестирования, но изученный контракт создания не подтверждает выбор каналов и перенос версий как в Play. Не обещать аналоги `internal`, `beta` и `promote`. |

### Числовые ограничения полей

| Поле | Максимальная длина |
| --- | --- |
| `whatsNew` | 5000 символов |
| `appName` | 50 символов |
| `shortDescription` | 80 символов |
| `fullDescription` | 4000 символов |
| `moderInfo` | 180 символов |

В 0.0.1 CLI меняет только `whatsNew`; остальные лимиты зафиксированы для будущей
поддержки карточки, они не добавляют новые флаги в текущую версию. Проверять UTF-8
и число символов, не размер текста в байтах; точный учёт составных символов сервером
проверить граничными примерами. Допустимые `partialValue`: 5, 10, 25, 50, 75, 100;
в 0.0.1 параметр частичной публикации не предоставляется.

## Стек и структура

Использовать Go, Cobra/pflag, `log/slog`, `encoding/json`, `archive/zip`, `crypto`,
`net/http`, `mime/multipart`, `testing` и `httptest`; сохранить
`google.golang.org/protobuf/encoding/protowire` для разбора манифеста AAB.
Использовать версию инструментов Go исходного проекта после проверки её доступности
на момент реализации (в изученном go.mod указано `go 1.27.3`). Зафиксировать
поддерживаемые версии в go.mod и CI. Для RuStore написать небольшой HTTP-клиент;
не переносить зависимости Google API, OAuth и ADC.

Использовать Makefile, golangci-lint, shellcheck, actionlint, govulncheck, Dependabot
и GoReleaser, как в исходном проекте. Собирать статические бинарные файлы для
Linux/macOS/Windows, amd64/arm64, с версией, коммитом и датой сборки, архивами
для выпуска и checksums.txt.

```text
cmd/rustore-publisher/main.go
internal/cli/        Команды Cobra, разбор флагов, вывод текста и JSON
internal/app/        Прямолинейные функции publish/status/doctor
internal/rustore/    Клиент, авторизация, типы API, ошибки и правила повторных попыток
internal/artifact/   Проверка AAB, данные из манифеста и SHA-256
internal/exitcode/   Стабильные категории ошибок процесса
internal/version/   Сведения о сборке
action.yml          Составное действие для публикации
setup/action.yml    Составное действие для установки CLI
scripts/            Скрипты установки и публикации, их тесты
docs/               Контракт CLI, настройка, архитектура, ошибки и действия
.github/workflows/  CI и выпуск версий
```

Зависимости: `cli -> app -> rustore/artifact`. Использовать конкретные структуры
и прямые вызовы. Где это нужно для тестирования, передавать HTTP-клиент, адрес API,
часы и потоки вывода через конструкторы. Добавлять небольшие интерфейсы только
при реальной необходимости у вызывающего кода. Не создавать универсальный интерфейс
магазинов, движок сценариев, DI-фреймворк, локальную базу данных, систему плагинов,
пакеты на будущее или общую библиотеку для нескольких магазинов. Логику повторных
попыток держать рядом с HTTP-клиентом. Референс — собственный проект того же
автора (`github.com/vyachin/google-play-publisher`), поэтому его код разрешено
переиспользовать (см. [ADR-0001](adr/0001-reuse-reference.md)). Без изменений
переносятся только нейтральные части: разбор AAB и проверки артефакта, каркас CLI
(`version`, `completion`, коды завершения), тестовые помощники `httptest`,
`Makefile`, конфигурация линтеров, GoReleaser, CI-workflow, `setup/`, `action.yml`
и `scripts/`. Play-специфика (клиент API, треки, статусы, OAuth/ADC) не переносится.
Лицензия должна быть в обоих репозиториях; перенос фиксируется в ADR и CHANGELOG.
Не переносить учётные данные или результаты сборки. Схему манифеста сверять с официальной схемой AOSP
[Resources.proto](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/tools/aapt2/Resources.proto),
соблюдая условия использования внешних зависимостей.

### Методы API, сверенные с документацией

Проверено по страницам документации 2026-11-09; ответы на живом аккаунте ещё
не сняты, поэтому структуры считаются ожидаемыми, а не гарантированными.

- `POST /public/auth/` принимает `keyId`, `timestamp` и `signature`. `timestamp` —
  строка с миллисекундами и смещением, например `2026-11-09T18:00:00.000+03:00`;
  отклонение от серверного времени не более 60 секунд. Подпись — SHA512withRSA
  от `keyId+timestamp` в Base64. Ответ: `code`, `message`, `body.jwe`,
  `body.ttl` (900 секунд) и `timestamp`.
- `GET /public/v1/application/{package}/version` — список версий. Параметры:
  `ids`, `versionStatuses`, `filterTestingType` (`ALL`, `RELEASE`, `ALPHA`;
  в документации встречается опечатка с кириллической `А`), `page` с нуля,
  `size` до 100. Ответ: `body.content[]`, `pageNumber`, `pageSize`,
  `totalElements`, `totalPages`.
- `GET /public/v2/application/{package}/version/{versionId}` — подробности.
  Используются `statusComment`, `permissions` (категория → `permission` и
  `description`), `packages[].verCode`, `isMainApk`, `servicesType` и
  `autoDetectedSdks` (категория → список), `testingType` (`ALPHA`, `BETA`,
  `PRODUCTION`).
- Поле типа версии в списке документация называет `filterTestingType`, а пример
  ответа содержит `testingType`. CLI принимает оба имени и не считает
  отсутствие поля явным null.
- `appType` в списке — `MAIN` или `GAME`, в подробностях — `MAIN` или `GAMES`;
  оба значения игр читаются как игры.
- `POST /public/v1/application/{package}/version` создаёт черновик и принимает
  `publishType` (`MANUAL`, `INSTANTLY`, `DELAYED`; по умолчанию API берёт
  `INSTANTLY`), `partialValue` и `whatsNew`; остальные поля наследуются от
  активной версии. Пример ответа содержит `body` с числом `versionId`, хотя
  таблица полей описывает объект `content`, поэтому CLI принимает обе формы.
  Создание нового черновика через API удаляет предыдущий.
- `POST /public/v1/application/{package}/version/{versionId}/aab` загружает AAB
  multipart-полем `file` и возвращает найденные `permissions` и
  `autoDetectedSdks`.
- `POST /public/v1/application/{package}/version/{versionId}/commit?priorityUpdate=0`
  отправляет черновик на модерацию. Известные сообщения об ошибке:
  `Packages for version with id = ... Is not found`, `Version must have at least
  one main non-HMS apk-file`, `Version must have not only HMS apk-file`.

## Предлагаемый контракт команд версии 0.0.1

Ниже — проект контракта, который нужно зафиксировать на этапе 1; CLI пока не реализован.

| Команда | Поведение |
| --- | --- |
| `publish -f app.aab` | Локальная проверка, проверка состояния в магазине, создание черновика с ручной публикацией, загрузка, отправка на модерацию, возврат ID версии и фактически известного статуса. |
| `status -p PACKAGE [--version-id ID]` | Чтение статуса, кода версии, режима публикации и комментария модерации, если он доступен. |
| `doctor -p PACKAGE [-f app.aab]` | Локальные проверки, авторизация и проверка доступа и состояния без изменений. Не создаёт и не загружает черновик. |
| `version`, `completion` | Те же соглашения, что в исходном CLI. |

Общие флаги: `--credentials`, `--json`, `--debug`, `--timeout`, `--request-timeout`.
Флаг `--draft` в версии 0.0.1 не поддерживается; отдельной досылки или удаления
существующего черновика нет. Успешный `publish` всегда подтверждает отправку на
модерацию либо явно возвращает `skipped=true` для уже отправленной версии.
`--dry-run` возвращает только результат предварительной проверки.
Сохранить `--package/-p`, `--aab/-f`, `--version-code`, `--metadata-dir`,
`--if-exists=fail|skip`. Флаги пакета и кода версии проверяют значения, прочитанные
из AAB; при несовпадении завершать работу до авторизации и обращения к сети.
Для `status` пакет задаётся явно. RuStore `versionId` и Android `versionCode` —
разные значения; различать их во флагах, типах, результатах и выходных параметрах действий.

Добавить `--publish-type=manual|instantly`, по умолчанию `manual`; дата публикации
не передаётся, поле `publishDateTime` в 0.0.1 отсутствует. Отложенная публикация
(`delayed`, `--publish-at`, окно даты, запас 30 минут, `PUBLISH_AT_MARGIN_LOW`)
перенесена в 0.0.2 и в 0.0.1 отклоняется как неизвестное значение с кодом 2.
Для `instantly` при отправке черновика командой `publish` требуется `--yes`;
для ручного режима — нет.
Ручной выпуск после одобрения и восстановление существующих черновиков выполняются
в консоли RuStore. Не добавлять отдельные команды submit/release и режим работы
с существующей версией в `publish`. Команда `publish` всегда работает с переданным AAB.

Сохранить `--dry-run`, определив его как локальную проверку и предварительную
проверку API только на чтение; без изменений в магазине. Явно описать отличие
от пробного запуска исходного проекта, который загружает файл и проверяет изменения.
Такой режим не гарантирует успешное прохождение модерации.

Не принимать специфичные для Play флаги `--track`, `--from`, `--to`, `--release-name`
и значения статусов Play. RuStore `appName` — название приложения, а не метка выпуска.
Неизвестные флаги должны приводить к понятной ошибке. Не переносить устаревшие
псевдонимы команд и параметров исходного проекта в новый CLI.

Файл учётных данных выбирается через `--credentials` или `RUSTORE_CREDENTIALS_FILE`:

```json
{"keyId":"KEY_ID","privateKey":"BASE64_PKCS8_RSA_PRIVATE_KEY_FROM_RUSTORE"}
```

Флаг имеет приоритет над переменной окружения. Содержимое секретов и подписи
не передаются аргументами CLI. Формат JSON выше — собственный формат CLI, а не
заявленный экспорт RuStore: документация описывает ID ключа и копирование значения
приватного ключа отдельно. Поддерживать только Base64 DER PKCS#8 с RSA, как
в примере Java из документации; PEM, PKCS#1 и произвольные JSON-экспорты пока
отклонять с понятной ошибкой. Не угадывать имена полей и формат ключа. Хранить токены только в памяти; исключать содержимое
запросов авторизации и `Public-Token` даже из отладочных логов.

В версии 0.0.1 поддержать только метаданные списка изменений со знакомой структурой:

```text
metadata/ru-RU/changelogs/42.txt
```

Разрешать только каталог локали `ru-RU`; это совместимость с раскладкой Play,
а не локализация API RuStore. Читать файл по коду версии AAB, явно сопоставлять
его полю `whatsNew`, проверять максимум 5000 символов до API. Любые другие локали
отклонять с кодом 2, не объединять переводы. Без `--metadata-dir` не передавать
`whatsNew` и предупреждать в stderr и JSON (`warnings` с кодом
`CHANGELOG_INHERITED`), что пользователи увидят прежние заметки активной версии.
Если `--metadata-dir` задан, но файла текущей версии нет или он пустой,
возвращать код 2, исключая случайное наследование при опечатке. Принимать `--metadata-dir` только для
этого сценария; отклонять файлы карточки, изображений и тестировщиков до реализации
их поддержки. Остальные метаданные редактируются в консоли.

Примеры после реализации:

```bash
export RUSTORE_CREDENTIALS_FILE=/path/to/rustore.json
rustore-publisher doctor -p com.example.app -f app-release.aab
rustore-publisher publish -f app-release.aab --metadata-dir metadata --json
rustore-publisher status -p com.example.app --version-id 123456
# После одобрения модерации опубликовать вручную в консоли RuStore.
```

## Публикация, ошибки и восстановление

1. Проверить флаги, формат учётных данных, структуру AAB и признаки подписи,
   размер, данные приложения и список изменений. Наличие признаков подписи
   не является полной криптографической проверкой подписи.
2. Пройти авторизацию; прочитать страницы версий и проверить активную версию,
   совпадающий код версии, существующие черновики и конфликтующие состояния
   модерации. Не считать первую страницу полным списком.
3. Отказаться от создания, если уже есть другой черновик. В версии 0.0.1 нет
   автоматической замены. Предварительное чтение не защищает от гонки с консолью
   или другим CI: явно описать это, требовать последовательной публикации
   и проверить поведение создания до выпуска приложения.
4. Создать черновик одним запросом, явно указав `publishType` в теле запроса
   создания, а не в commit. Для MANUAL и INSTANTLY всегда передавать
   `partialValue=100`, не наследуя процент активной версии. Прочитать итоговые
   настройки и подтвердить полный охват; если сервер не сохранил 100%, остановиться
   до загрузки с `REMOTE_STATE_MISMATCH`, не исправлять настройки молча.
   Сохранить ID версии и выполнить серверную сверку, описанную ниже.
5. Передавать multipart из файла потоком, без загрузки всего AAB в память.
   Обновлять токен перед долгой загрузкой; не предполагать поддержку частей
   или возобновления. Где возможно, сверять данные версии через методы подробностей
   и статуса; проверить их доступность после загрузки.
6. После подтверждённой загрузки ограниченно ждать готовности AAB (правила ниже),
   затем отправить на модерацию с `priorityUpdate=0`. Повтор commit допустим только
   после подтверждённого отказа «пакеты ещё не готовы», в общем бюджете обработки. Отдельного
   флага или входного параметра действия для приоритета в 0.0.1 нет. При ошибке
   сохранить черновик, вернуть ID версии и инструкции восстановления через консоль.
7. Успешную отправку обозначать `submitted`, а не `published`. По возможности
   прочитать текущий статус; ошибка последующего чтения не должна отменять
   подтверждённую отправку. Дальнейшие результаты модерации и публикации получать
   через `status`.

`--if-exists=skip` не заменяет восстановление черновика. Проверять все страницы
и тип версии: совпадение в тестовом канале не заменяет релизную публикацию.
Следующая таблица применяется к совпавшему пакету и коду релизной версии,
определённой по явному `testingType=null` ответа списка (правила нормализации ниже).
`sendDateForModer` с корректной непустой датой — доказательство отправки; также
достаточны известные статусы после commit, включая AUTO_CHECK. Неправильную дату
не считать доказательством. Отказ, архив или DRAFT имеют приоритет над исторической
датой отправки: не пропускать отклонённую версию только из-за заполненной даты.

| Состояние | Результат publish |
| --- | --- |
| `AUTO_CHECK`, `TAKEN_FOR_MODERATION`, `MODERATION`, `READY_FOR_PUBLICATION`, `ACTIVE`, `PARTIAL_ACTIVE`, `PREVIOUS_ACTIVE` | С `skip` — код 0, `skipped=true`, существующий `version_id` и реальное состояние; с `fail` — код 5. |
| `DRAFT` | Код 5, `EXISTING_DRAFT`, `skipped=false`, `version_id`, инструкция закончить или удалить черновик через консоль. Даже при `skip` это не успех. |
| `REJECTED_BY_MODERATOR`, `REJECTED_BY_SECURITY`, `AUTO_CHECK_FAILED` | Код 7, `VERSION_REJECTED`; не пропускать как успех. |
| `ARCHIVED` | Код 5, `VERSION_UNAVAILABLE`; не считать доступным выпуском. |
| `DELETED_DRAFT` | Не считать успешной версией или живым черновиком; возможность новой загрузки решает обычная проверка активного кода и API. |
| Неизвестный статус | При корректном sendDateForModer и отсутствии явного отказа — с skip код 0, с fail код 5; без доказательства отправки — код 5, `VERSION_STATE_CONFLICT`. Сохранить сырой статус и предупреждение `UNKNOWN_REMOTE_VALUE`. |

Наличие другого живого черновика блокирует создание с кодом 5 и его ID, но не
мешает вернуть подтверждённый no-op при уже отправленной совпавшей версии.
Не добавлять opt-in удаление: при пяти командах сознательно оставляем восстановление
через консоль. Повторный CI после неудачной отправки может потребовать ручной работы.
Это идемпотентность по коду версии, а не доказательство совпадения файла с SHA-256.
При нескольких неоднозначных совпадениях возвращать конфликт, не выбирать наугад.

### Тип версии, сверка отправки и выбор status

Query `filterTestingType` использует только ASCII-константы `ALL`, `RELEASE`,
`ALPHA`; не копировать кириллическую А из опечатки `RELEАSE`. Имена query и полей
ответа различаются: нормализовать фактическое `testingType`, а не выдуманное поле
`filterTestingType` внутри ответа. До выпуска проверить сырые ответы и записать
фикстуры; пример документации с некавычённым alpha не является валидным JSON.
Для проверки конфликтов черновиков читать ALL, чтобы не пропустить тестовый черновик.

Для списка: явное `testingType=null` -> `testing_type=release`; строка alpha без
учёта регистра -> alpha; другие строки или отсутствующее поле -> unknown с сохранением
сырого значения. Отсутствие поля не приравнивать к null. Сопоставление detail-значения
PRODUCTION с релизной версией не использовать для skip без подтверждённой фикстуры.
В 0.0.1 skip применим только к подтверждённой релизной версии. Не угадывать тип по
одному query-фильтру. appType GAME и GAMES читать как игры, исходное значение
сохранять; при будущей записи использовать GAMES, для неигровых приложений — MAIN.

После потерянного ответа commit сверять именно известный versionId, package,
versionCode, тип версии и sendDateForModer или статус после commit. Подтверждённая
отправка завершает команду как submitted; новый запрос commit не отправлять.
DRAFT без даты сразу после таймаута не доказывает, что предыдущий commit не сработает:
при отсутствии доказательства сохранять неизвестный результат.

`status --version-id ID` возвращает ровно указанную версию; ID из тестового канала
разрешён для чтения, с явно указанным типом. Без ID выводить `latest_release` —
релизную версию с максимальным versionCode, исключая DRAFT и DELETED_DRAFT, включая
отклонённые и архивные версии с их реальным статусом. При равенстве выбирать
максимальный versionId. Отдельное поле `draft` содержит живой черновик независимо
от типа; отсутствие элемента — null. Если несколько живых черновиков противоречат
контракту API, вернуть `VERSION_STATE_CONFLICT`, не выбирать произвольно.
Прочитать все страницы. При отсутствии релизов вернуть latest_release=null;
успешное чтение существующего приложения остаётся кодом 0. Чтение отклонённой
версии командой status тоже код 0: код 7 относится к операции публикации.

### Серверная сверка созданной версии

После создания, до передачи большого файла, прочитать детали и список по ID:
сверить ID, publishType, partialValue и whatsNew, если changelog был передан.
Для отсутствующего changelog не требовать пустого whatsNew.
После загрузки перед commit повторить сверку с конечным состоянием обработки.
Для MANUAL и INSTANTLY охват должен быть 100; наследование процента активной
версии считается несовпадением.

Если чтение временно отстаёт, использовать ограниченные чтения в доступном бюджете;
не начинать upload/commit без подтверждения полей. Доказанное несовпадение либо
недоступность обязательного поля — код 5, `REMOTE_STATE_MISMATCH`, ID и список
отличий, без автоматического PATCH или publish-settings. Сетевая ошибка сверки —
обычная сетевая категория, а не доказательство несовпадения. Поле whatsNew
сравнивать с точным отправленным текстом после документированной локальной
нормализации перевода строк. Заметки 42 не подменять текстом активной версии.

Автоматически повторять только безопасные чтения и запросы токена при временных
сетевых ошибках, 429 и 5xx. Использовать ограниченную экспоненциальную задержку
со случайным разбросом и учётом Retry-After. Не повторять вслепую создание
черновика, загрузку и отправку после неоднозначной ошибки. Где возможно,
проверять результат по ID и статусу версии; иначе возвращать `outcome_unknown`
и инструкции проверки. Ограниченный повтор commit после полного подтверждённого
отказа из-за неготовности пакетов — отдельное исключение, описанное ниже. Не удалять черновик после неоднозначной отправки.
Сохранять черновики после ошибок и отмены для восстановления; в версии 0.0.1
нет автоматической очистки. Потеря ответа на создание тоже означает неизвестный
результат, даже если ID версии не получен.

Проверять HTTP-статус и `code` ответа RuStore. Сохранять полезные сообщения API
после удаления секретов. Отсутствие настроенной подписи и новые декларации
чувствительных разрешений должны сопровождаться инструкцией ручного действия;
запрещённые разрешения и некорректные сборки считать отклонением.

Категории кодов завершения: 0 — успех, 1 — внутренняя ошибка, 2 — ввод,
3 — авторизация или доступ, 4 — объект не найден, 5 — конфликт,
6 — временная ошибка или неизвестный результат, 7 — отклонение,
8 — ручное исправление настроек магазина, 130 — прерывание сигналом.

В версии 0.0.1 код 8 имеет закрытый список `error.code`:

- `AAB_SIGNING_REQUIRED` — API явно сообщает о ненастроенной подписи AAB.
- `PERMISSION_DECLARATION_REQUIRED` — API явно требует декларации новых чувствительных разрешений в консоли.

`manual_action=true` только для этих двух ошибок и кода 8. Это признак ручного
исправления, блокирующего операцию CLI, а не любого будущего действия человека.
При успешной отправке в MANUAL — код 0 и `manual_action=false`; необходимость
позднейшего выпуска определяется `publish_type=manual`, статусом и сообщением.
Существующий черновик — код 5 и `manual_action=false`; потерянный ответ записи —
код 6 и `outcome_unknown=true`, не код 8. Запрещённые разрешения — код 7.
Не классифицировать неизвестные ошибки как код 8 по общим словам сообщения:
использовать проверенные ответы API; иначе обычная категория HTTP/API-ошибки.

При неоднозначной записи её неизвестный результат имеет приоритет над общей
классификацией 401/5xx. При сигнале код 130 имеет приоритет; поле
`outcome_unknown` сохраняет сведения о незавершённой записи. Для ошибок чтения,
известного отказа до записи и ожидания конвертации без commit это поле false.

### JSON-контракт и закрытые перечисления

С `--json` выводить ровно один объект в stdout, включая ошибки; логи — stderr.
Машинная схема — [schema/result.schema.json](schema/result.schema.json), примеры —
в [schema/examples](schema/examples). Соответствие примеров схеме проверяется
контрактным тестом. Изменять перечисления только вместе с версией схемы
и документацией; сырые значения RuStore не расширяют наши enum.

Объект publish/doctor/status содержит `schema_version=1`, `command`, `package`,
`version_code`, `version_id`, `phase`, `outcome`, `version_status`, `testing_type`,
`testing_type_raw`, `publish_type`, `partial_value`, `whats_new`,
`send_date_for_moder`, `submitted`, `published`, `skipped`, `manual_action`,
`outcome_unknown`, `permissions`, `auto_detected_sdks`, `warnings`, `error`.
Идентификаторы и versionCode — целые числа или null; строки — string/null;
permissions/auto_detected_sdks — object/null. Поля отражают факты, не намерение:
неизвестные submitted/published — null, skipped/manual_action/outcome_unknown — bool.
`submitted=true` при непустом `sendDateForModer`, иначе false. `published=true`
для `ACTIVE`, `PARTIAL_ACTIVE`, `PREVIOUS_ACTIVE` и `ARCHIVED`, false для
остальных известных статусов и null для неизвестного.
Отсутствующее testingType различать с явным null внутри парсера. В JSON
`testing_type` — release|alpha|unknown, сырое поле хранить в testing_type_raw.
`publish_type` — manual|instantly|unknown|null; version_status сохраняет
строку RuStore. Массив warnings содержит объекты code/message; error — null
при успехе либо объект code/message/hint. status дополнительно содержит
`latest_release` и `draft` того же формата фактов о версии без рекурсивных результатов;
без --version-id верхние поля одной версии null, сведения находятся в этих объектах;
с --version-id верхние поля заполнены, а `latest_release` и `draft` равны null.

Закрытый `phase`: `preflight|auth|create|upload|processing|commit|status`.
Сверка сразу после создания относится к create, после загрузки — processing.
У doctor/status итоговая фаза status; локальная ошибка и version/completion-ошибка
относятся к preflight. Фаза ошибки фиксирует место сбоя.

Закрытый `outcome`: `submitted|skipped|dry_run|inspected|failed|unknown`.
Первые три — publish, inspected — успешный doctor/status, failed — известная ошибка,
unknown — недоказанный результат записи и outcome_unknown=true. Для обычной ошибки
чтения использовать failed. При сигнале с неопределённой записью — unknown и код 130.
Успешный `version --json` — отдельный объект `schema_version`, `command`, `version`,
`commit`, `build_date`; ошибки `version` и `completion` используют общий объект
результата. `completion` без `--json` выводит скрипт оболочки, с `--json` — ошибку
`INVALID_ARGUMENTS` и код 2.

аккаунте и зафиксировать санитарно очищенные ответы, без новых error.code.

Последний используется, если commit точно принят, но последующее чтение не удалось;
успех submitted при этом сохраняется. Текст сообщения не используется для ветвления.

### Диагностика разрешений и SDK

Сохранять необязательные `permissions` и `autoDetectedSdks` из ответа загрузки
как `permissions` и `auto_detected_sdks` в результате `publish --json`, включая ошибки следующих фаз. Если API их не
вернул, использовать null, не выдавать отсутствие данных за пустой список.
Показывать краткие сведения в обычном выводе и сводке GitHub Action. Не объявлять
любое найденное разрешение новым или требующим декларации: это должно следовать
из явного ответа API или подтверждённого сравнения, иначе данные информационные.
Обнаружение платёжного или рекламного SDK само по себе не является ошибкой.

`doctor` остаётся операцией без записи: не загружает локальный AAB ради определения
SDK. Может показывать декларации разрешений и SDK из подробностей активной версии,
с явным указанием её ID и источника (`permissions` и `packages[].autoDetectedSdks`).
Эти данные не выдаются за результат анализа переданного локального файла.
Если сведения недоступны, сообщать об этом; не обещать локальное обнаружение SDK.

### Восстановление черновика через консоль

Черновик API виден сразу, но бинарный файл, загруженный API, может не отображаться
в консоли до отправки на модерацию. Поэтому не предлагать «посмотреть файл в консоли»
как способ подтвердить успешную загрузку. Сначала использовать `status` и подробности
API по известному ID. Вернуть ID, package, versionCode, фазу ошибки и состояние.

При подтверждённом DRAFT предложить открыть приложение и черновик в консоли,
дозаполнить декларации или заново загрузить AAB через консоль при необходимости,
затем отправить на модерацию. Конкретную доступность редактирования API-черновика
в консоли проверить на тестовом приложении; если такой путь недоступен, предложить
вручную удалить именно этот черновик и после проверки состояния повторить publish.
Не обещать возможность повторного использования кода версии после удаления.
При неизвестном результате commit сначала проверить, не началась ли модерация;
до выяснения не предлагать удаление или замену файла.

API допускает обновление AAB внутри того же `versionId`; это не возобновляемая
передача и не доказанная идемпотентность при потерянном ответе. Возможный будущий
повтор загрузки должен использовать тот же файл и ID, свежий токен, подтверждённый
DRAFT и отсутствие commit в полёте. В 0.0.1 автоматическую перезагрузку после
неоднозначной ошибки и режим восстановления через CLI не добавляем. Не создаём
новый черновик ради повторной загрузки. Это ограничение CLI, а не ограничение API.

`version --json` возвращает объект с `version`, `commit`, `build_date`.
`completion` выводит непосредственно скрипт оболочки. Сочетание `completion --json`
завершается кодом 2 и одним JSON-объектом ошибки без фрагментов скрипта.

### Ожидание обработки AAB

В 0.0.1 включить `--processing-timeout=2m`: бюджет начинается после успешного
ответа загрузки, включает чтения и все допустимые попытки commit и не сбрасывается
при повторе. Интервал — 5 секунд; каждый запрос ограничен остатком бюджета
и общим таймаутом. Это ожидание обработки файла, не модерации или публикации.

В изученной документации нет отдельного поля готовности конвертации. Подробности
содержат `packages[].verCode`, `isMainApk`, `servicesType`; проверять совпавший код
и основной пакет с подходящим типом сервисов. Значения servicesType и достаточность
такого критерия подтвердить на тестовом приложении; Unknown или отсутствие поля
не считать доказательством non-HMS. `DRAFT` и HTTP 200 сами по себе не доказывают
готовность. Не добавлять выдуманное поле конвертации.

Сначала опрашивать подробности. Если подтверждённый критерий готовности доступен,
commit вызывать после него. Если чтения не дают надёжного признака, допускается
проверочная отправка после подтверждённой загрузки. Далее различать результаты:

- Полный ответ API `code=OK` — отправка подтверждена, прекратить повторы.
- Полный ответ с явным отказом `Packages for version with id = ... is not found`
  для текущего ID — кандидат на временную неготовность после успешной загрузки.
  Подтвердить чтением, что версия ещё DRAFT; подождать 5 секунд и повторить commit
  в том же двухминутном бюджете. Точный шаблон ответа и отсутствие перехода
  на модерацию зафиксировать тестами и проверить на реальном приложении до выпуска.
  Не повторять commit, пока предыдущее состояние не подтверждено.
- Отказ `Version must have at least one main non-HMS apk-file` повторять только
  если чтение подтверждает ещё не завершившееся появление пакетов после загрузки
  и такой временный сценарий проверен. Если пакеты уже есть и все HMS, это ошибка
  сборки (код 7), а не повод ждать. Отсутствие данных само по себе не доказывает
  незавершённую конвертацию; неоднозначный вариант не включать в список повторов.
- Таймаут, обрыв, 5xx или неполный ответ commit не являются подтверждённой
  неготовностью. Только чтение и сверка результата; без слепого повтора.
  Если результат не доказан — код 6 и `outcome_unknown=true`.
- Остальные ошибки, включая декларации разрешений, не повторять по этому правилу.

Такая политика повторов — решение CLI, а не заявленная гарантия API об
асинхронной конвертации. Если загрузка фактически блокируется до готовности,
не вводить лишнее ожидание. До выпуска проверить весь сценарий на тестовом
приложении, включая локальные тесты «not found -> готовность -> OK» и «commit
принят, ответ потерян -> повтор не выполняется».

При истечении бюджета без commit либо только после подтверждённых отказов
возвращать код 6, `AAB_PROCESSING_TIMEOUT`, `outcome_unknown=false`, ID и инструкцию
восстановления. Если была неоднозначная попытка commit, не заменять её результат
ошибкой конвертации: сохранять `outcome_unknown=true`. Явная ошибка конвертации —
код 7. Черновик автоматически не удалять и AAB заново не загружать.

### Таймауты и токены

- `--timeout=30m` — общий бюджет всей команды по умолчанию: локальные проверки,
  авторизация, загрузка, обработка и commit. Явный 0 отключает ограничение;
  отрицательные значения — ошибка ввода. Такой же default 30m у Action.
  Отключение лимита — осознанное отличие от положительного timeout референса.
- `--request-timeout=2m` — бюджет одного обычного запроса, включая авторизацию и чтения,
  но не потоковую загрузку AAB. Повторные попытки ограничены общим и фазовым бюджетом.
- У загрузки нет короткого таймаута всего запроса; на неё действует общий `--timeout`
  и отмена. Ограничить установку TCP/TLS-соединения 10 секундами на этап, ожидание
  заголовков ответа — 2 минутами после передачи тела. Не задавать `http.Client.Timeout=2m`
  для загрузки. Зависшее отправление прерывается сигналом, общим таймаутом или лимитом CI.
- `--processing-timeout=2m` — отдельный бюджет готовности после ответа загрузки;
  положительное значение обязательно. Он не продлевает общий `--timeout`.

Хранить срок токена по `ttl`, обновлять за 60 секунд до истечения; при `ttl <= 60`
считать ответ авторизации непригодным, не входить в бесконечный цикл обновления.
Перед каждой загрузкой обязательно получить свежий токен. Обновление токена
не меняет заголовок уже отправленного HTTP-запроса и не продлевает его действие.
Документация не гарантирует, как проверяется токен при загрузке дольше 900 секунд;
проверить этот сценарий, не обещать поддержку произвольной длительности.

Для безопасного чтения после 401 разрешить одно обновление и один повтор.
Загрузку после 401, таймаута или обрыва после начала передачи автоматически
не повторять: сначала пытаться прочитать состояние с обновлённым токеном.
Если результат не доказан, вернуть код 6, `outcome_unknown=true`, `phase=upload`
и известный ID с инструкцией проверить консоль. Наличие совпавшего кода версии
не доказывает целостность полного AAB. Для однозначного отказа авторизации до
передачи — код 3 и `outcome_unknown=false`. При прерывании сигналом — код 130.


## Контракт GitHub Actions

Предоставить два составных действия, вызывающих выпущенный бинарный файл:

- `vyachin/rustore-publisher@v0.0.1`: установка, `publish --json`, выходные параметры и сводка задания.
- `vyachin/rustore-publisher/setup@v0.0.1`: только установка, для любой команды CLI.

Это примеры будущих тегов; они пока не объявлены существующими.
Первоначально поддерживать те же среды действий, что в исходном проекте:
Linux amd64/arm64. Архивы CLI остаются кроссплатформенными. Поддержку других ОС
для запуска действий можно добавить отдельно.

Входные параметры публикации: `version`, `package`, `aab`, `credentials-file`,
`credentials-json-base64`, `metadata-dir`, `version-code`, `publish-type` (manual),
`if-exists` (fail), `dry-run` (false), `yes` (false),
`timeout` (30m), `request-timeout` (2m), `processing-timeout` (2m), `debug` (false). Параметры учётных данных взаимоисключающие.
`credentials-json-base64` кодирует весь JSON учётных данных, в отличие от поля
privateKey в Base64 внутри этого JSON. Алиас `credentials-base64` не добавлять:
опубликованной совместимости ещё нет; использовать однозначное имя с первого выпуска.

Выходные параметры: `version-code`, `version-id`, `outcome`, `version-status`,
`submitted`, `published`, `skipped`, `manual-action`, `error-code`,
`outcome-unknown`, `phase`, `testing-type`, `result-file`. Передавать результат ошибки до возврата
ненулевого кода CLI. Сводка должна различать незавершённую загрузку, отправку на модерацию,
ожидание ручного выпуска и публикацию. Предупреждения из JSON, включая
`CHANGELOG_INHERITED`, выводить в сводке.

Установка выбирает явно указанную версию CLI или тег выпуска действия,
скачивает соответствующий архив, сверяет SHA-256 с checksums.txt и обновляет PATH
через GITHUB_PATH. При запуске с ветки или SHA без определяемого тега выпуска
требовать версию. Не скачивать последнюю версию молча. Проверять версию,
платформу и имена файлов; при несовпадении контрольных сумм прерывать установку.

Передавать параметры через переменные окружения и массивы Bash с корректным
экранированием; не использовать eval и прямую подстановку выражений GitHub
в команды оболочки. Ограничивать права временных файлов, скрывать учётные данные
и токены, при выходе удалять созданные действием файлы секретов. Не удалять файл
учётных данных вызывающего workflow. Не включать секреты в сводки и результаты.

Описать предлагаемый workflow для использования после сборки и подписи AAB:

```yaml
concurrency:
  group: rustore-com-example-app
  cancel-in-progress: false
permissions:
  contents: read
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      # Собрать AAB здесь или скачать результат задания сборки.
      - uses: vyachin/rustore-publisher@v0.0.1
        with:
          version: 0.0.1
          package: com.example.app
          aab: app/build/outputs/bundle/release/app-release.aab
          credentials-json-base64: ${{ secrets.RUSTORE_CREDENTIALS_BASE64 }}
          metadata-dir: metadata
```

После одобрения модерации выпустить версию с ручным режимом через консоль RuStore.
Действие setup поддерживает пять согласованных команд CLI, включая чтение статуса.
Группы concurrency в GitHub координируют запуски только внутри одного репозитория;
публикации из других репозиториев и консоли требуют дополнительного согласования.
Не держать среду выполнения занятой несколько дней в ожидании модерации.

## Проверка на реальном приложении

- Тесты записи запускаются только с `RUSTORE_LIVE_TEST=1`; иначе пропускаются.
  Это единственный признак разрешения тестам создавать версию и отправлять её
  на модерацию. CLI publish сам по себе этим тестовым флагом не ограничивается.
- Обязательны `RUSTORE_LIVE_PACKAGE`, `RUSTORE_LIVE_AAB`,
  `RUSTORE_LIVE_VERSION_CODE` и путь в `RUSTORE_CREDENTIALS_FILE`. Не печатать секреты.
- Сборка выполняется снаружи; CI сборки использует единый возрастающий счётчик
  для приложения с известной нижней границей выше уже использованных кодов.
  Не полагаться на один `github.run_number` разных workflow или репозиториев.
- Для каждого нового прогона записи резервировать новый код. При повторном запуске
  после неизвестного результата сначала проверять прежний ID; не скрывать его
  созданием следующей версии. Чисто читающие проверки нового кода не требуют.
- Тест сверяет код из манифеста с `RUSTORE_LIVE_VERSION_CODE`, проверяет версии
  и черновики через API, а затем публикует с `--if-exists=fail` в MANUAL.
  Код не должен быть ранее использован; все пишущие задания сериализуются.
  Обнаруженный конфликт приводит к отказу до создания, а не к изменению AAB.
- CLI не переписывает manifest и не генерирует код версии. Глобальную уникальность
  обеспечивает сборка и координация всех публикующих систем; API остаётся
  окончательной проверкой при гонке. Определённый `concurrency` не блокирует консоль.
- Ручной выпуск после модерации выполняется в консоли; тесты автоматически его
  не выполняют. Дальнейшее чтение статуса может использовать тот же ID.
