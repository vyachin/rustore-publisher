# Метаданные карточки: описания, иконка и скриншоты

Исследование возможности передавать из `--metadata-dir` не только список
изменений и контакты, но и тексты карточки, иконку и скриншоты. Документ
фиксирует возможности RuStore Public API и ограничения, которые нужно решить
до реализации. Живые запросы к RuStore при подготовке не выполнялись: выводы
сделаны по документации API на 2026-11-10.

## Краткий вывод

- Public API RuStore **позволяет** задать `appName`, `shortDescription`
  и `fullDescription` при создании черновика, а также загрузить иконку
  и скриншоты отдельными multipart-запросами.
- Тексты карточки уже передаются: `publish` читает `ru-RU/title.txt`,
  `short_description.txt` и `full_description.txt` и заполняет `appName`,
  `shortDescription` и `fullDescription` при создании черновика.
- Иконка загружается из `ru-RU/images/icon.png` или `icon.jpg` и проверяется
  по `iconUid`/`iconUrl`. Скриншоты пока перечисляются в `METADATA_IGNORED`.
- Для скриншотов нужны загрузка, чтение списка и, возможно, удаление. Это
  операции записи, требующие своего порядка и проверки результата.
- Локалей в Public API нет: у карточки один набор текстов и изображений.
  Раскладка Google Play с несколькими локалями не переносится один к одному;
  использовать можно только `ru-RU`, остальные локали остаются
  в `METADATA_IGNORED`.
- Главный нерешённый вопрос — наследование и замена скриншотов в черновике.
  Без живой проверки нельзя безопасно удалять «лишние» скриншоты: неизвестно,
  являются ли они копиями черновика или общими объектами с активной версией.

## Что умеет Public API

| Что | Метод | Ограничения |
| --- | --- | --- |
| Название, краткое и полное описание | `POST /public/v1/application/{packageName}/version` | `appName` ≤ 50, `shortDescription` ≤ 80, `fullDescription` ≤ 4000 символов. Не переданное поле наследуется из активной версии |
| Исправление черновика | `PATCH /public/v2/application/{packageName}/version/{versionId}` | Только до отправки на модерацию; поля и лимиты те же |
| Иконка | `POST /public/v1/application/{packageName}/version/{versionId}/image/icon` | Ровно 512×512 px, `.jpeg` или `.png`, ≤ 3 МБ, поле `file` |
| Скриншоты | `POST /public/v1/.../image/screenshot/{orientation}/{ordinal}` или `POST /public/v2/.../image/screenshot/{orientation}/{ordinal}/{type}` | `.jpg`/`.png`, ≤ 5 МБ, стороны 320–3840 px, 16:9 или 9:16, одна ориентация, `ordinal` 0–9, для публикации нужно минимум 3 |
| Список скриншотов | `GET /public/v2/application/{packageName}/version/{versionId}/image/screenshot` | Постранично, возвращает `id`, `ordinal`, `orientation`, `type`, `fileUrl` |
| Удаление скриншота | `DELETE /public/v2/application/{packageName}/version/{versionId}/image/screenshot/{id}` | Удаляет скриншот черновика по идентификатору |
| Проверка результата | `GET /public/v2/application/{packageName}/version/{versionId}` | Возвращает `appName`, `shortDescription`, `fullDescription`, `iconUrl`, `iconUid`, `fileUids[]` |

Типы скриншотов в v2: `SCREENSHOT` (телефон), `TABLET_SCREENSHOT`,
`TV_SCREENSHOT`. В v1 тип не передаётся.

Ограничения и особенности:

- минимальное количество скриншотов для публикации — 3, максимум активных —
  10; при загрузке большего числа предыдущие становятся неактивными;
- нельзя смешивать горизонтальные и вертикальные скриншоты;
- `ordinal` задаёт позицию, а не уникальность: повторная загрузка в тот же
  `ordinal` заменяет активный скриншот;
- видео карточки задаётся ссылкой (`video`, `backgroundVideo`), а не файлом;
- метода загрузки feature graphic / promo graphic в Public API нет;
- в подробностях версии есть `iconUidTv` и `iconUrlTv`, но отдельного метода
  загрузки ТВ-иконки в изученном списке методов не найдено;
- локалей нет ни в одном из перечисленных методов.

## Как это ложится на каталог metadata

Предлагаемое соответствие знакомой раскладке:

```text
metadata/
├── ru-RU/
│   ├── title.txt                 # appName, ≤ 50
│   ├── short_description.txt     # shortDescription, ≤ 80
│   ├── full_description.txt      # fullDescription, ≤ 4000
│   ├── images/
│   │   ├── icon.png              # 512×512, ≤ 3 МБ
│   │   ├── phoneScreenshots/     # SCREENSHOT, 3–10 файлов
│   │   ├── tenInchScreenshots/   # TABLET_SCREENSHOT, необязательно
│   │   └── tvScreenshots/        # TV_SCREENSHOT, необязательно
│   └── changelogs/
│       └── 42.txt
└── developer-contacts.json
```

Правила, которые вытекают из возможностей API:

- читается только `ru-RU`; `en-US` и другие локали не публикуются
  и попадают в `METADATA_IGNORED`. Это осознанное расхождение с Google Play:
  у RuStore одна карточка на приложение;
- для текстов отсутствующий файл означает «не менять, унаследовать из активной
  версии». Пустой файл или нарушение лимита — ошибка до обращения к сети,
  чтобы опечатка не привела к случайному наследованию;
- иконка необязательна: `images/icon.png` или `images/icon.jpg`, ровно
  512×512, PNG/JPEG, до 3 МБ, только один файл. Без файла иконка наследуется;
  после загрузки `iconUid` и `iconUrl` меняются на новые;
- `title.txt` меняет название приложения; это осознанное поведение. Файл
  необязателен: без него название наследуется из активной версии;
- для скриншотов имена файлов сортируются, `ordinal` считается от 0.
  Отсутствие каталога — не трогать изображения; пустой каталог — ошибка
  (удалять скриншоты в первой версии не планируется); 1–2 файла — ошибка
  (для публикации нужно минимум 3), больше 10 — ошибка, а не молчаливое
  усечение;
- ориентация определяется по размерам: ширина больше высоты — `LANDSCAPE`,
  иначе `PORTRAIT`. Смешивать ориентации в одном каталоге нельзя;
- `featureGraphic.png`, `promoGraphic`, `wearScreenshots` и прочие файлы без
  поддержки в API остаются в `METADATA_IGNORED`;
- ТВ-версии полей (`shortDescriptionTv`, `fullDescriptionTv`, `whatsNewTv`)
  и ТВ-иконка в первый объём не входят.

## Порядок публикации

Безопасный порядок такой:

1. Прочитать и проверить все локальные файлы: лимиты, UTF-8, форматы
   изображений, размеры, ориентацию, количество. Ошибки — до создания
   черновика.
2. Создать черновик, передав описания в теле запроса.
3. Сверить описания в подробностях версии.
4. Загрузить иконку и сверить `iconUid`/`iconUrl`.
5. Загрузить скриншоты — следующий этап.
6. Сверить список скриншотов после его реализации.
7. Загрузить AAB, дождаться обработки, отправить на модерацию.

Проверки до создания черновика важны: `publish` не умеет возобновлять
существующий черновик, поэтому ошибка после создания оставляет ручную уборку
в консоли.

Загрузка скриншота идемпотентна по ключу «версия + `ordinal`»: повтор
с тем же файлом заменяет активный скриншот, а не создаёт дубликат. Живая
проверка иконки подтвердила смену `iconUid`; поведение при повторной загрузке
того же файла ещё не проверено. После сетевого сбоя можно не гадать,
а прочитать `iconUid` или список скриншотов и либо подтвердить результат,
либо повторить запрос.

## Риски и открытые вопросы

1. **Наследование изображений.** Иконка черновика наследуется из активной
   версии — это подтверждено живой проверкой. Для скриншотов наследование
   не описано. Если черновик их копирует, загрузка трёх новых в ordinal 0–2
   оставит старые 3–9; тогда для точной замены нужно удалять лишние через
   `DELETE`, а это разрушающая операция.
2. **Общие объекты.** Не доказано, что скриншоты черновика — его собственная
   копия. Если `DELETE` в черновике затрагивает активную версию, удаление
   недопустимо. Это главный аргумент проверить поведение на тестовом
   приложении до реализации удаления.
3. **Минимум 3 скриншота.** Пользователь может хранить в metadata один-два
   файла для другого магазина; CLI должен явно отказать, а не загрузить
   неполный набор.
4. **Точный размер иконки.** Требуется ровно 512×512, а не просто квадрат.
   Формат и размер файла проверяются локально.
5. **Локали.** Перенести несколько локалей Google Play в RuStore нельзя.
   Нужно явно документировать, что используется только `ru-RU`.
6. **Совместимость поведения.** Тексты карточки публикуются автоматически при
   `--metadata-dir`. Если в каталоге уже лежат тексты Play, после обновления
   они начнут применяться к RuStore. Это задокументировано в README и
   CHANGELOG; отдельный флаг не вводится.
7. **Проверка загрузки.** У иконки нет отдельного метода чтения, кроме
   `iconUrl`/`iconUid` в подробностях версии. Если сервер дедуплицирует файл
   и не меняет `iconUid`, доказать замену по API не получится. Для
   скриншотов можно сравнить количество, `ordinal`, `orientation` и `type`,
   но не содержимое файла.
8. **Коды ошибок.** Добавлен `INVALID_METADATA` (код завершения 2); схема
   JSON, `docs/design.md`, README и CHANGELOG обновлены.

## Предлагаемый объём

Этап 1 — тексты. Реализован: `appName`, `shortDescription` и
`fullDescription` передаются полями существующего запроса, ошибки локальных
файлов дают `INVALID_METADATA`, результат сверяется по подробностям версии.

Этап 2 — иконка. Реализован: один multipart-запрос, результат проверяется
по `iconUrl`/`iconUid`; Content-Type части должен быть `image/png` или
`image/jpeg`, иначе API отвечает 400.

Этап 3 — скриншоты. Только после живой проверки наследования и замены.
Если черновик наследует изображения, понадобится `GET` списка и `DELETE`
лишних; правила удаления нужно описать явно. Если не наследует — достаточно
загрузки и проверки списка.

Этап 4 — планшетные и ТВ-скриншоты, ТВ-тексты, видео по ссылке и `PATCH`
для восстановления черновика. Каждый пункт расширяет контракт и должен
проверяться отдельно.

## Результаты живой проверки 2026-11-10

- Черновик с `appName`, `shortDescription` и `fullDescription` создан через
  Public API; `VersionDetail` вернул все три значения без дополнительной
  нормализации, включая многострочное полное описание.
- Черновик удалён тем же ключом; версия в списке не осталась.
- До загрузки иконки черновик наследовал `iconUid` активной версии; после
  загрузки API вернул новый `iconUid` и `iconUrl`. При неверном Content-Type
  части API ответил 400 «Можно загрузить только .jpeg или .png», после
  исправления на `image/png` загрузка прошла.
- Полный `publish` с загрузкой AAB не выполнялся, чтобы не создавать версию
  ниже уже находящейся в модерации 42. Передача полей, иконки и чтение ответа
  проверены, но отображение карточки после модерации ещё не проверено.
- Наследование и замена скриншотов остаются открытыми.

## Что проверить на живом аккаунте

- копирует ли создание черновика скриншоты активной версии;
- что будет при повторной загрузке того же файла иконки;
- заменяет ли загрузка в существующий `ordinal` старый скриншот и остаются ли
  активными скриншоты с бо́льшими номерами;
- затрагивает ли `DELETE` скриншота в черновике активную версию;
- какое сообщение и код возвращает `commit` при одном-двух скриншотах;
- доступны ли описания и изображения в подробностях версии сразу после
  загрузки;
- действительно ли сервер принимает 5 МБ для скриншота (в старых обзорах
  упоминается 3 МБ);
- как проверяется соотношение сторон: отказ или предупреждение.
