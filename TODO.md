# rustore-publisher — план реализации 0.0.1

Репозиторий: `github.com/vyachin/rustore-publisher`. Команды: `doctor`, `status`,
`version`, `completion`, `publish`. Основная реализация выполнена; ниже сохранён
первоначальный план, а результаты ревью добавлены отдельным разделом.

Подробный контракт перенесён в [docs/design.md](docs/design.md) — единственный
источник правил CLI/API/JSON/ошибок/Actions. Здесь остаются задачи и критерии
готовности; исторические ответы из чата не дублируют спецификацию.
Правила языка и разработки — в [AGENTS.md](AGENTS.md).

### Ошибки публикации — P1

- [ ] **R01. Сохранять неизвестный результат записи при сетевых сбоях и неполном ответе.**
  Места: `internal/rustore/client.go:123–143`, `internal/rustore/auth.go:188–218`,
  `internal/rustore/write.go:34–40`, `internal/rustore/upload.go:92–129`.
  `OUTCOME_UNKNOWN` сейчас выставляется преимущественно при HTTP 5xx, но создание
  и commit могут примениться до EOF, таймаута, ошибки чтения тела или невалидного
  успешного JSON. Воспроизведение: обрыв соединения после запроса создания даёт
  код 6 `API_UNAVAILABLE`, `outcome_unknown=false`; обрезанный JSON — код 1
  `API_RESPONSE_INVALID`, тоже false. Подсказка предлагает повторить команду,
  хотя черновик мог быть создан. При отмене загрузки также возвращается голый
  `ctx.Err()` без признака неопределённой записи.
  Исправление: учитывать вид операции и возможность отправки запроса; при
  недоказанном исходе сохранять unknown, известный ID и безопасную подсказку.
  Для commit выполнять только чтение восстановления; для сигнала сохранять
  код 130 вместе с unknown. Проверить потерянный ответ, обрезанный JSON,
  неполное HTTP-тело, request timeout, общий timeout и отмену каждой записи.

  **Почему это ошибка.** Клиент наблюдает доставку ответа, а не транзакцию
  на сервере. Сервер может сохранить черновик и потерять соединение до передачи
  ID. Повтор создания потенциально заменит чужой или только что созданный
  черновик. Аналогично отсутствие ответа commit не доказывает отсутствие
  отправки на модерацию. Для безопасных чтений такой неопределённости записи нет.

  **Порядок исправления.** В HTTP-слое разделить подготовку запроса, выполнение
  и разбор ответа. Локальная ошибка до обращения к транспорту не является
  неизвестной записью. После начала выполнения пишущего запроса без полного
  подтверждения результата выбирать консервативный unknown; не пытаться
  доказывать отсутствие записи только типом сетевой ошибки. Некорректный
  `body.versionId` после ответа создания `code=OK` тоже не означает, что создание
  не состоялось. Передавать исходную причину через Unwrap, а неопределённость
  записи хранить отдельно от причины остановки команды: это позволит сохранить
  unknown при кодах COMMAND_TIMEOUT и INTERRUPTED. Успешное восстановление commit
  разрешать только по правилам R08. Не выполнять повторную запись для проверки.

  **Как проверять.** Подменный сервер должен сначала изменить своё состояние,
  затем закрыть соединение либо вернуть повреждённый ответ. Проверить отдельно
  create, upload и commit; счётчик каждой записи должен остаться равным одному.
  В JSON проверить phase, известный ID, outcome_unknown и подсказку. Для commit
  добавить оба варианта чтения: доказанная отправка даёт успех, недоказанный
  исход сохраняет unknown. Контрольные тесты: локальная ошибка файла и ошибка
  авторизации до начала upload не становятся неизвестной загрузкой.

  **Как проверять.** Проверять журнал методов и URL, а не только итоговую ошибку.

- [ ] **R06. Ограничивать запросы и ожидания остатком processing-timeout.**
  Места: `internal/app/publish.go:205–213`, `:250–280`, `:302–313`.

  команда ждёт примерно 105ms, затем выполняет commit и возвращает успех.

  request-timeout дополнительно ограничивает отдельный запрос. Паузы ограничить
  остатком, HTTP-повторы должны видеть тот же фазовый контекст. Если commit
  начат и потерял ответ при истечении времени, сохранять unknown по R01,

  fallback в docs/design.md и затем обновить тесты.

  **Как проверять.** Контролируемый HTTP-сервер должен задерживать детали дольше
  фазового бюджета и фиксировать отмену запроса; нового commit после исчерпания
  бюджета быть не должно. Отдельно проверить Retry-After и backoff, длинный
  PollInterval, более короткий общий timeout, готовность в начале этапа и fallback
  при пустых packages. Не проверять точное число миллисекунд на загруженной CI;
  проверять отмену, последовательность операций и отсутствие нового полного бюджета.

- [ ] **R12. Требовать EOF после единственного объекта локального JSON.**
  Места: `internal/app/credentials.go:51–60`, `internal/app/contacts.go:37–41`.
  LoadCredentials не проверяет хвост после первого объекта. Контакты отвергают
  второй корректный JSON, но принимают SyntaxError и UnexpectedEOF при второй
  Decode. Воспроизведение: `{"email":"dev@example.com"} broken` принимается
  без ошибки. Исправление: после Decode принимать только `io.EOF`;
  тестировать второй объект, незавершённый объект и произвольный мусор.
  Основание: [контракт json.Decoder.Decode](https://pkg.go.dev/encoding/json#Decoder.Decode).

  **Почему это ошибка.** Decoder предназначен в том числе для потока нескольких
  JSON-значений. Успешный первый Decode не подтверждает корректность всего файла.
  Любая ошибка второго Decode, кроме EOF, означает, что хвост не является
  допустимыми завершающими пробелами. Сейчас повреждённая конфигурация может
  использоваться для реальной публикации без сообщения пользователю.

  **Порядок исправления.** В обоих загрузчиках после успешного первого Decode
  выполнить второй Decode в временную переменную: EOF означает конец файла,
  nil — лишнее значение, любая другая ошибка — повреждённый хвост. Сохранить
  DisallowUnknownFields и существующие категории ошибок. При выводе ошибки
  credentials не включать содержимое privateKey и всего файла. Общую небольшую
  функцию добавлять только если она упрощает оба места, без фреймворка конфигурации.

  **Как проверять.** Один объект, объект с пробелами и переводами строк,
  два объекта, объект плюс null, массив в хвосте, незакрытая скобка и произвольный
  текст. Только первые два варианта успешны. Для credentials использовать
  сгенерированный тестовый ключ; убедиться, что ошибка не печатает его значение.

- [ ] **R13. Проверять булевы входы Action до запуска публикации.**
  Место: `scripts/publish.sh:129–134`.
  Только точная строка `true` включает dry-run; любое другое значение молча
  отключает его. Воспроизведение с подставным CLI: `RUSTORE_DRY_RUN=TRUE`
  завершает скрипт кодом 0, но аргумент `--dry-run` не передаётся. Ошибка
  конфигурации может запустить настоящую запись вместо проверки.
  Исправление: принимать явно определённые true/false, при необходимости
  нормализовать регистр; все остальные значения отвергать до запуска CLI.
  Проверить false, true, TRUE, опечатку и строку с пробелами.

  **Почему это ошибка.** Вход составного Action приходит как строка. Текущая
  проверка приравнивает любое значение, отличное от true, к разрешению реальной
  публикации. Ошибка в защитном флаге поэтому меняет магазин вместо отказа

  аргумент --dry-run до CLI вообще не доходит.

  **Порядок исправления.** В начале скрипта нормализовать dry-run и debug
  по одинаковой явной политике. Например, разрешить true/false без учёта регистра,

  создания файла секрета и запуска CLI. Сообщение должно называть неверный вход

  **Как проверять.** Подставной CLI должен фиксировать аргументы и сам факт
  запуска. true/TRUE передают --dry-run, false/FALSE не передают. Опечатка,
  числовое значение и строка с пробелами завершают скрипт ненулевым кодом,
  CLI не запускается. Проверить, что default false остаётся совместимым.

### Улучшения сопровождения

- [ ] **U01 / P2. Исправить учёт Retry-After.** `internal/rustore/auth.go:241–253`:
  jitter вычитается после применения серверного интервала, а затем интервал
  ограничен 30s. Например, Retry-After=60 приводит к ожиданию 15–30s.
  Применять jitter к локальному backoff и сохранять серверный минимум;
  если он не помещается в бюджет, завершать попытки. Проверять формат заголовка
  строго и добавить детерминированные тесты секунд и HTTP-date.
  Основание: [HTTP Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after).

  **Почему.** Сервер сообщает, сколько требуется ждать до следующего обращения.
  Вычитание jitter из этого значения делает следующий запрос преждевременным.
  При ограничении частоты это увеличивает число 429 и ухудшает восстановление.

  **Как решить.** Сначала вычислить локальную экспоненциальную задержку
  с ограничением и jitter; затем взять максимум из неё и серверной задержки.
  Локальный предел 30s не должен сокращать серверное указание. Проверять целое
  число секунд строго, без fmt.Sscanf, принимающего числовой префикс мусорной
  строки; защититься от переполнения duration. Поддержать HTTP-date. Если пауза
  не помещается в оставшийся бюджет, не запускать очередной запрос. Гигантский
  заголовок не должен приводить к переполнению или бесконечному ожиданию.

  **Как проверять.** С управляемыми часами и Sleep проверить, что Retry-After=60
  никогда не превращается в паузу меньше 60s; при бюджете 10s нового запроса нет.
  Добавить будущую и прошедшую HTTP-date, 0, пустую строку, отрицательное число,
  `60garbage` и очень большое число. Не проверять конкретное случайное значение:
  проверять допустимые границы либо подменить генератор jitter.

- [ ] **U02 / P2. Не скрывать ошибки автоматического обнаружения контактов.**
  `internal/cli/publish.go:168`: только os.IsNotExist означает отсутствие

  неизвестной команды и ошибок манифеста. Проверить, что error.code, JSON-поля,
  имена флагов и исходные сообщения API не изменились при переводе.

- [ ] **U05 / P3. Усилить тесты поведения на границах.** Добавить постоянные
  регрессионные тесты R01–R13, особенно состояния и последовательности HTTP,
  а также fuzz-тесты protobuf-манифеста. Часы Now/Sleep использовать согласованно
  для детерминированных бюджетов. Не закреплять слабое доказательство загрузки
  текущим TestPublishRecoversUploadAfterServerError: сначала определить
  достаточное подтверждение результата по R03.

  **Почему.** Успешный сценарий и отсутствие замечаний линтера не подтверждают
  безопасность повторов и точность JSON. Часть существующих тестов закрепляет
  текущее слабое поведение восстановления, поэтому зелёный CI может сохраняться
  при нарушении контракта.

  **Как решить.** При каждом исправлении сначала добавить регрессионный тест,
  падающий на исходной реализации. Проверять наблюдаемые факты: запись выполнена
  один раз, после отказа commit отсутствует, сервер получил проверенные байты,
  JSON согласован с exit code. Использовать таблицы для матриц состояний,
  локальные HTTP-серверы для протокола и подставной CLI для Bash. Не использовать
  фиксированные Sleep как сигнал готовности сервера: передавать готовность
  каналом. Fuzz-тестам манифеста дать небольшие валидные и повреждённые seed;
  инварианты — отсутствие panic, завершение на ограниченном входе и корректные
  категории ошибок. Не вводить большой слой моков или новый DI-фреймворк.

  **Как проверять.** На исходном коде каждый регрессионный сценарий должен
  демонстрировать исправляемый дефект, после исправления — проходить. Запускать
  затронутые тесты, затем `go test -race ./...`, vet, линтер и Bash-тесты.
  Fuzz запускать ограниченное время отдельно. Для проверок времени допустим
  повторный запуск небольшого набора, чтобы обнаружить нестабильность;
  многократный прогон всего проекта без причины не нужен.

### Рекомендуемый порядок исправлений

1. R01 и R05: единая модель причины остановки и неизвестного результата,
   согласованное формирование JSON. Это основа обработки ошибок остальных этапов.
2. R08, R03 и R04: доказательство отправки, отказ от слабого восстановления upload,
   безопасные условия повторного commit.
3. R06 и R02: общий фазовый бюджет, резерв для fallback и конечная сверка настроек.
4. R07, R09, R10, R12, R13 и U02: порядок preflight, стабильность артефакта,
   строгий локальный ввод и входы Action.
5. R11, U01, U03 и U04: полный контроль JSON, задержки, воспроизводимость CI
   и согласованная документация. U05 выполняется вместе с каждым исправлением.

Каждый пункт закрывать после проверки его наблюдаемого результата, обновления
контракта при необходимости и проходящих проверок. Реальный RuStore нужен
для подтверждения недокументированных свойств API; он не нужен для большинства
описанных регрессионных тестов и не должен вызываться обычным CI.
